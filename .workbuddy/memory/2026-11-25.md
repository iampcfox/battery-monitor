## 任务栏窄条启动空白问题（src/TaskbarStrip.cs）

用户反馈：启动后任务栏窄条右侧留一大片空白。

### 根因（以运行日志为准，不信 README/开发指南）
- 日志 `tb ok:` 显示窄条贴托盘（x=864），TM（TrafficMonitor，pid 17728，`#32770`）被压到 600–733，
  窄条右侧 733→864 留下空白。
- 旧代码用 `_tmOffset = wr - listRight`（TM 右缘相对按钮容器右缘的偏移）反推目标宽度，
  并在 `_forced` 时冻结该偏移。实测右扩容器时 TM 不跟着走（wr 停在 682、listRight 到 731），
  偏移从 135 突变到 −49，推算失效 → 空白。开发指南 §4.4「TM 跟着容器右缘走」不成立。

### 改动（A+B，已落地）
- 删除 `_tmOffset` / `tgtW` / `floorW` / `canCompress` / `WidenTo` 整套推算逻辑。
- 占位只按实测：规划拍（窄条宽度变化）用 `reread()` 重取任务栏矩形，
  按 TM 右缘到托盘的实测缺口压缩按钮区，压完立刻重测。
- 落点 A：贴 TM 右缘，无 TM 才贴托盘。
- 诊断日志新增 `tmGap=x-wr`、`winW`，正常 tmGap≈6。

### 第二轮：右侧空白仍在（用户截图）
- 日志显示 A 生效（tmGap=6），但窄条窗口只画紧凑内容宽度 116，右边 855→986 仍空。
- 改为：有蓝牙段时窗口宽度 `winW = rightEdge - x`（右缘顶到托盘，整块吃下空地）；
  `BuildLayout(g, segs, fillW)` 把多出的宽度摊到本机各段间距（NumX/ValRight/MainW），
  蓝牙区贴右缘；无蓝牙设备时保持紧凑宽度。
- 验证：编译被环境安全策略拦截，交用户本地 `编译并启动.cmd`，待反馈。

### 第三轮（最终）：真正根因 = 窄条压缩了任务栏本身
- 用户指出那块空白是「系统任务栏自己的宽度」，且任务栏经 Explorer Patcher 修改。日志坐实：
  `15:04:15 MSTaskSwWClass [96,954] 858px`（自然宽，铺满 ReBar）→
  `15:04:27 ReBarWindow32 [94,986] 不变，MSTaskSwWClass [96,598] 502px`（被 CompressTo 压掉 351px）。
- Explorer Patcher 下 ReBar 宽度固定贴托盘、不跟 MSTaskSwWClass 缩，压窄容器后 598→986
  一段没有任务按钮，就是那块空白；TM 是浮动第三方窗，跟着容器右缘从 855 跑到 600。
- 摊开内容填空白只会把 3 个 90% 拉散，更难看（用户否）。
- **最终方案（用户选「不碰任务栏布局」）**：完全撤销对任务栏的压缩/还原/自愈
  （删 CompressTo/RestoreContainer/SelfHealReserve/WriteReserveMarker 及 `_forced` 等字段），
  窄条像 TM 一样浮在任务栏右侧：贴 TM 左缘、无 TM 贴托盘；窗口宽度 = 紧凑内容宽度，
  撤销摊开（BuildLayout 去掉 fillW/ExtraGap/segN）；放不下减段、减不掉 Hide。
  代价：窄条盖住最右边约一个任务按钮（和 TM 盖按钮同性质），但任务按钮铺满、零空白。
- 诊断日志 `tb ok:` 保留 x/w/winW/list/btn/tm/tray；正常态 winW==w、无 forced 字段。

### 第四轮：TrafficMonitor 源码解剖（C:/Projects/TrafficMonitor-master，只读）
- TM 有**两套**占位策略，按任务栏结构选（不是按 OS 版本）：
  - `CheckWindows11Taskbar()` 看 Shell_TrayWnd 下有无 `Windows.UI.Composition.DesktopWindowContentBridge`（TrafficMonitor.cpp:1303-1315）。
  - 有 → `CWin11TaskbarDlg`（Win11TaskbarDlg.cpp）：**不压缩**，贴托盘左缘；官方 Help.md:22-28 承认占满时重叠"目前无法解决"。
  - 无（有 ReBar+MSTaskSwWClass）→ `CClassicalTaskbarDlg`（ClassicalTaskbarDlg.cpp）：**MoveWindow 压缩按钮容器**，不遮挡。
  - 用户日志同时有 ReBar[94,986] 和 MSTaskSwWClass[96,598] → 走压缩分支，这就是 TM 不挡 Chrome 的原因。
- **压缩算法（ClassicalTaskbarDlg.cpp:15-38，全文核心）**：
  `容器新宽 = 容器原宽 − 自身宽`；`MoveWindow(m_hMin, left_space, 0, 新宽, 高, TRUE)`；
  `自身 x = left_space + 新宽 + 2`。压缩量就是自身宽度，压完自己立刻占住那块——不算缺口、不推算偏移。
- **自愈基准（TaskBarDlg.cpp:460-501）**：每轮 force_adjust 先 `ResetTaskbarPos()` 把容器还原到 `m_rcMinOri`（未压缩快照）→ 重新 GetWindowRect 测量 → 再压缩。基准永远干净。
- TM 挂到 `ReBarWindow32`（ClassicalTaskbarDlg.cpp:99-102），不是 Shell_TrayWnd；100ms 轮询，宽度变化/托盘变化才重排。
- TM 没有的：无标记文件崩溃自愈（全仓搜索确认），无浮条间互相避让，Win11 原生任务栏占满时自己也重叠。
- **关键结论**：deskband 不是唯一解。抄 TM 要抄对三件事——① 压缩量=自身宽（不是算缺口）；② 压完自己贴到容器新右缘+2；③ 每轮先还原原始快照再重压（我们之前 _forced 冻结基准是错的）。

### 第十轮：面板卡死修复（UI 线程被 WMI 阻塞）
- **症状**：WinUI 面板打开后"未响应"（SendMessageTimeout 返回 0，IsHungAppWindow 命中）。
- **根因**：`DevicesPage.Refresh()` 在 UI 线程同步调 `Sensors.Read()`，其中有多条
  `ManagementObjectSearcher` WMI 查询（BatteryStatus/BatteryTemperature/Win32_Battery/
  MSAcpi_ThermalZoneTemperature）+ 蓝牙 WinRT 反射调用（每台设备 `Wait(400)`），累计阻塞数秒到数十秒。
- **修法**：
  1. `DevicesPage` 改 `async Task RefreshAsync()`：`await Task.Run(() => Sensors.Read())` 后台采集，
     回 UI 线程只做控件赋值；新增 `_busy` 防重入（WMI 慢时定时器不叠加）、`_loadedOnce` 防缓存页重复初始化。
  2. `App` 构造里的 `History.Init`（读 CSV）也挪进 `Task.Run`，避免启动期阻塞。
- **验证**：同会话 60 秒、每 2 秒 `SendMessageTimeoutW` 探测，`hung=0`（之前必然 hung）。
- **另一个坑（重要）**：bash 里 `./exe &` 启动的进程会随命令会话结束被回收，
  导致误判"进程崩溃/闪退"。测存活必须**同一会话内启动+探测**，或用 PyInstaller 式 detached 启动。
- `编译并启动面板.cmd` 之前两个 bug 已修：路径 `C://Program Files` 双斜杠（if exist 失败→pause）、
  文件是 LF 换行（cmd 必须 CRLF）+ UTF-8 中文乱码；现为纯 ASCII + CRLF。

### 占位改成「落点绝对定位 + 只调容器宽度」（修窄条右侧那条空当）
**现象**：只开本程序 `list=[96,864] x=864`（右缘 980，距托盘 6px ✓）；
和 TM 一起 `list=[229,832] x=834`（右缘 950，距托盘 36px ✗）。同样 w=116，右边凭空多 30px。

**根因**（两个程序共用 `MSTaskSwWClass`，基准互相污染）：
- TM 的两个窗口占 96~362，容器左缘由它决定；我们原来用「容器当前宽 − 自身宽」算压缩量，
  而那个宽度里已经含了 TM 让出的部分，叠着再减一次 → 多压三十几像素。
- 原来每轮 `RestoreContainer()` 还原到 `_oriW` 快照 + 固定 `_leftSpace`，快照到底含不含 TM 那一段说不清；
  还原时还会把容器铺到 TM 身上（日志能看到 `list=[229,832] tm=[229,362]` 重叠一拍），shell 再推开 → 基准又变。
- `FindWidget` 从容器左缘扫，TM 夹在中间时会被当成"右侧浮条锚点"，落点算出 x=229/362（窄条往左闪）。

**改法**：
- 新增 `PlaceX(w, rightEdge, listLeft, btnRight, hasWidget, wl, gap)`：① 贴托盘左缘 `rightEdge-w`
  → ② 让右侧浮条 → ③ 不盖按钮（`btnRight+2`）→ ④ 不越过容器起点。**贴托盘优先**，右侧不留空当。
- 新增 `SetContainerWidth(list, targetW)`：`SetWindowPos(..., SWP_NOMOVE|SWP_NOZORDER|SWP_NOACTIVATE)`
  **只改宽度、左缘一个像素不动**（左缘归 shell 和 TM 管），宽窄双向可调，收敛三轮。取代 `CompressTo`。
- 规划改成：先算 `wantX`（理想左缘，贴托盘/让浮条，**不看当前按钮多大**）→
  `targetW = (wantX-2) - listLeft` → SetContainerWidth → 重测 btnRight/浮条 → 最后 `PlaceX` 定落点。
  不再有「还原快照 → 重压」两步，`_leftSpace` 字段删除，`RestoreContainer`/`SelfHealReserve` 也都改成只改宽度。
- 减段循环里也同步调容器宽度并重测按钮右缘。
- 日志新增 `rg=`（窄条右缘到托盘缝的余量），正常应为 0。
- 预期日志：无 TM `x=864 list=[96,862] btn=862 rg=0`；有 TM `x=864 list=[362,862] btn=862 rg=0`。
- 静态检查 0 错误 0 警告；需用户重编 + 重启进程验证。

#### 返工：第一版用 SetWindowPos(SWP_NOMOVE) 是错的
**现象**：用户重编后"只剩本机电量"，蓝牙和温度都没了；日志 `list=[96,919] btn=986 rg=-67` 与 `btn=919 rg=0` 交替，w 一直 59。
**根因**：`SetWindowPos + SWP_NOMOVE` 只改了容器宽度，**shell 不会重排容器里 `MSTaskListWClass` 的按钮** →
按钮停在原处、溢出到窄条下面（`btn=986 > listRight=919`）→ 每拍都判定"放不下"→ 减段循环
把温度、蓝牙一路 TrimOne 删掉 → 每拍 w=59，看起来"只剩电量"。
**为什么之前 MoveWindow 版按钮会跟着缩**：只有 `MoveWindow` 会触发 shell 重新布局列表子窗口。
**修法**：
- `SetContainerWidth` 改回 `MoveWindow`，但 x 用**每轮当前实测左缘**（不写死 `_leftSpace`/快照），
  等于只动右缘；收敛三轮，每轮重读左缘 → 不会把容器拉回去压 TM（那才是之前"越压越左"的原因）。
- 减段加保护 `listOverflow = btnRight > listRight + 4`：按钮溢出容器时不减段（减了也解决不了，只会丢信息）。
- 溢出时落点改成"贴托盘硬放"（可能盖住最后一个按钮的尾巴），既不删内容也不 Hide。
- `targetW` 加上限 `_oriW`：托盘识别飘一下时别把容器撑得比自然宽还宽。
- 教训：**改容器宽度必须用 MoveWindow**；SetWindowPos 只改尺寸不会让 shell 重排按钮。

#### 点托盘「向上箭头」窄条闪烁：定位 + 修复
**现象**：点击托盘抽屉箭头时窄条闪一下（内容消失/只剩 59px 电量）。
**定位手法**（`dev/probe-flicker*.py`，纯 ctypes，25ms 采样）：
- 同时采 `MSTaskSwWClass/ReBarWindow32/TrayNotifyWnd/Button` 矩形、窄条自身矩形、
  `WindowFromPoint(条中心)` 落在谁身上、条那块像素的 md5。
- 结论一（浮窗态）：盖住期间 `WindowFromPoint` 落在 `ReBarWindow32` → 是**任务栏把顶层浮窗压下去了**
  （explorer 打开抽屉时把 Shell_TrayWnd 重新抬到最上层），下一拍 Sync 要 1 秒才抬回来 = 闪一下。
- 结论二（嵌入态）：点箭头会让 shell 把容器宽度**还原成自然宽度**（890），而重排判据只看窄条宽度 w，
  w 没变就不重压 → 按钮顶着容器伸到托盘边 → 减段循环把温度/蓝牙全删 → w=59。

**修法（src/TaskbarStrip.cs）**
- `KeepAbove()` + 50ms `_z` 定时器：`WindowFromPoint` 探中心点，往上找根是 Shell_TrayWnd 才抬；
  挤到任务栏正上方（`ZAnchor()`，任务栏是 topmost 时插它后面），不是顶到 HWND_TOPMOST 最顶 ——
  这样不会盖住抽屉/右键菜单。Sync 里的抬升也改成同一个锚点。
- 重排判据加 `listReset`：`_plannedListW` 与容器实际宽度差 >2 且**按钮区伸进了窄条要占的那段**
  （`listRight > rightEdge - w`）就重压；加这个条件是为了不跟 shell/TM 反复改同一条容器。
- **还原必须连左缘一起**：以前 `RestoreContainer`/`SelfHealReserve` 只还原宽度，
  被强杀后左缘已漂到中间 → 自然宽度套在漂移后的左缘上 → 容器越过托盘 → shell 重排把按钮区推到中间，
  任务栏左边一大片空白、窄条只剩 59px。新增 `RestoreNatural()`（左缘+宽度一起），
  标记文件 `battery-monitor.taskbar` 改成 `左缘,宽度`（兼容老格式只有宽度），启动加一次性 `left drift` 自愈。
- 教训：**容器宽度/位置都是一对，只还原一半必然越用越歪**；托盘重排会悄悄还原容器，重排判据不能只看内容宽度。

#### 蓝牙三连修：闪烁 / 无电量不显示 / 每设备音量
1) **没连的设备偶尔冒出来**（手柄）根因在 `KickLinkRefresh` 的回调：`_linkCache = map` 整体替换，
   某轮 `QueryLink` 400ms 超时 → 该地址不在 map → `BtLinkCached` 返回 null → 调用方按"未知"放行
   → 没连的手柄闪一下又消失。改成"问到才更新、没问到保留旧结论"，连续 3 轮问不到才删（`_linkMiss`）。
   另加 `_btPct`（地址→电量，30 秒记忆）：设备偶发不报电量时沿用上次值，避免因 -1 而闪。
2) **没电量的设备不进窄条/悬浮窗**：`TaskbarStrip.BtWithPower()` + `CardRender.VisibleBt()` 过滤 `Percent<0`；
   面板设备页读 `s.Bt` 原样保留（用户要求只在面板看）。
3) **每个设备各自的音量**：`Audio.cs` 新增 `EnumAudioEndpoints` 枚举播放端点，
   开 `IPropertyStore` 读 `PKEY_Device_FriendlyName` / `PKEY_Device_ContainerId`，
   `MatchEndpoint(container, model)` 先按容器 ID、再按端点名里的型号配对，读该端点自己的
   `IAudioEndpointVolume.GetMasterVolumeLevelScalar`。实测：QCY 耳机 30%、IN糖 音箱 100%。
   注意：本机端点容器 ID 与蓝牙设备容器 ID 对不上（端点那串像端点序号），实际走的是名字匹配。
4) 顺带：IN糖 是音箱却被判成"耳机1"，导致 QCY 显示成"耳机2"。新增 `Audio.KindHint()`——
   Windows 端点名叫"扬声器 (…)"就是音箱、"耳机 (…)"才是耳机；只在判成耳机时用它纠一次。

#### 托盘悬停提示改成多行（一行一台设备）
**坑**：WinForms `NotifyIcon.Text` 超过 **63 字符**直接抛 ArgumentException（实测 "文本长度必须少于 64 个字符"），
撑不到 127；而一行一台设备的表格（标题 + 本机 + N 台设备）很容易超。
**做法**（用户选"先按 63 字符做压缩版"）：
- `TrayIcon.BuildTip()` 拼行：`Battery Monitor` / `92% 充电中 40℃` / `耳机1 30% 83` / `音箱 --`；
  没电量的设备写 `--`；音频设备在图尾带当前音量（`Audio.VolumeFor`）。
- `Fit()` 按优先级裁：先试"标题+全部行"，超了丢标题，再超才从尾部丢设备行。
- 实测当前设备组合正好 63 字符：`Battery Monitor | 92% 充电中 40℃ | 耳机1 30% 83 | 耳机2 70% 39 | 音箱 -- 100`。
- 日志加了 `tray tip(长度)` 便于核对（超 63 会抛异常）。
**待确认**：Windows 11 托盘提示是 XAML 画的（EnumWindows 里找不到 tooltips_class32 窗口，自动化悬停验证不了），
5 行是否全部显示需要用户肉眼看一眼；若被折叠，下一步只能自己用 Shell_NotifyIcon 接管托盘（szTip 128 字符）。

#### 横向布局重叠/间隔修复
**现象**：耳机行的音量数字叠在电池胶囊上、设备间隔忽大忽小。
**根因**：画的时候胶囊右缘少加了 4px 缝（`x + capW` 应为 `x + 4 + capW`）→ 胶囊压名字、音量压胶囊；
且小喇叭的宽度测量用 8、绘制用 9.2，两处不一致；每台设备画完用"重新累计的 x"，误差会往后累积。
**修法**：胶囊右缘补上缝；小喇叭宽度统一 `iconBox*0.8`；每台设备画完直接 `x = segStart + DevW[i]`，
以量出的段宽为准，误差不外溢；设备间隔 9→13、块间隔 10→12。
#### 间隔不匀（第二轮）
真根因：名字后的 4px 缝让了两次（`x += labelW+4` 之后胶囊右缘又 `+4`），画出来的段宽比量出来的宽 4px，
段尾再对齐回量出值就会把每台设备的尾巴吃掉 4px，间隔看起来忽大忽小。
修法：胶囊右缘 `= x + capW`（缝只让一次）。用"整列空白像素"量化：三台设备间隔 16/13/15px，基本均匀。
